# Waypoint local web prototype

On Windows, build the prototype from the repository root with:

```powershell
./apps/web_app/scripts/build-windows.ps1
```

The helper requires Rust and the MSVC build tools. It checks for a compatible x64 OpenSSL developer installation in the standard `Program Files/OpenSSL-Win64` and `Program Files/OpenSSL` locations; pass `-OpenSslRoot` or set `OPENSSL_DIR` to use another installation. If none is available, it downloads the pinned, signed OpenSSL 4.1.0 x64 MSI, verifies it and extracts the development files into `target/waypoint-openssl-4.1.0` without installing OpenSSL system-wide. Provisioning needs network access and at least 1 GiB of free disk space; the download is about 58 MiB. For offline setup, pass `-OpenSslInstaller <path>` with that exact MSI. A verified existing cache is reused. Incomplete or modified caches are rejected and retained for inspection. The helper builds one job at a time by default and copies the OpenSSL runtime next to `target/debug/waypoint_web.exe`. Add `-Release` for a release build. Rust and MSVC are not installed by this helper.

Release builds request Rust's static C runtime by default; debug builds retain Cargo's caller-supplied CRT settings. Use `-StaticCrt` to request static CRT explicitly, or `-StaticCrt:$false` to retain the caller's settings for a release build. The build receipt and package manifest record whether the helper requested static CRT; they do not verify the resulting imports. Bundled components may still have their own runtime requirements, and clean-host installation remains unverified. See `docs/g1/WINDOWS_STATIC_RELEASE_2026-11-01.md` in the source repository for the release-build evaluation.

The helper places the OpenSSL runtime and receipt next to the executable reported by Cargo, including with a custom target directory. When a later build uses a different OpenSSL DLL with the same name, the helper replaces it only if the previous Waypoint build receipt identifies the existing file. It keeps the old DLL in `waypoint-openssl-backups` beside the executable. An unrecognized DLL is left untouched.

Use `./apps/web_app/scripts/build-windows.ps1 -Test` to run the web-app tests or `./apps/web_app/scripts/build-windows.ps1 -Clippy` to lint its targets with warnings treated as errors. Both commands configure the same detected OpenSSL paths as the build.

To run a specific ignored integration test, use `-Test -Ignored -TestFilter <test-name>`. Inspect its prerequisites first: ignored tests can start local browsers, access the network or require installed tools.

For development tests, use `./apps/web_app/scripts/build-windows.ps1 -Test`; add `-TestFilter <name>` to run one test. The helper configures the same OpenSSL environment for tests as for builds.

Start the resulting executable to open the local browser workspace. On Windows, use the notification-area menu to reopen the workspace or exit; double-click the icon to reopen it. The Windows default build uses SQLCipher for the workspace database with a key protected by the current Windows account's DPAPI. When an existing plaintext workspace is migrated, the original database is deliberately retained and the interface reports that it remains on disk; protect it as private data. Application-record folders remain readable as requested. The prototype does not send applications from its interface.

For application inspection, an explicit `WAYPOINT_BROWSER` executable takes priority, followed by installed browsers and then any bundled Chromium fallback. Bundled browsers do not update automatically; replace them through a newly reviewed package when needed.

Use an up-to-date installed browser for employer sites. Chrome for Testing and Chromium snapshots do not update themselves; Chromium's [security guidance](https://github.com/chromium/chromium/blob/main/docs/security/faq.md#what-is-the-threat-model-for-chrome-for-testing) limits Chrome for Testing to trusted content. Waypoint does not currently install or update a browser automatically.

Public-board and batch web searches continue while the local app is running even if the web page is closed. Board results are saved incrementally. The latest web-search batch is sealed to the Windows user for recovery after restart; an active batch is normally checkpointed every five seconds and saved once more at normal shutdown. An interrupted batch is shown as incomplete and is not automatically resumed. A crash can lose pages since the last checkpoint, and the interface reports checkpoint or completed-history saving failures.

After upgrading an existing workspace, duplicate checking revisits older requisitions in the background. It checks at most one eligible job or skips a page of 64 jobs per scheduled step, and resumes after interruption. Existing duplicate decisions are retained. The interface reports the recheck while it is running; duplicate search waits for indexing to finish. The comparison remains bounded and can miss matches.

Up to 100 selected search links are sealed and restored from the workspace. Selecting a link does not inspect or apply for it. If another window changes the selection, reload before saving further changes.

The executable and its OpenSSL DLL must be distributed together. Installation, portable dependency provisioning, backup and key recovery are not yet complete. See `docs/WEB_PROTOTYPE_CHECKPOINT.md` for current capabilities and limitations.

The project uses free local tools and must not require paid APIs. Wider-web search uses a user-configured SearXNG-compatible provider; use a free or self-hosted instance. The app cannot determine an independent provider's pricing or guarantee its availability. Local-model features use Ollama rather than a paid inference API.

To create a local prototype ZIP after a build, use Python 3.11 or newer:

```powershell
./apps/web_app/scripts/build-windows.ps1 -Release
python ./apps/web_app/scripts/package-windows.py --release --output ./prototype-local/waypoint-release.zip
```

The output path must be new and inside the repository. The packaging step checks the build receipt, collects local license files for the Windows runtime dependency graph, and downloads a pinned Python 3.12 x64 runtime into the bundle. For offline packaging, provide the matching NuGet archive with `--python-package <path>` and the pinned PDF wheels with `--wheel-dir <path>`. Their SHA-256 digests are checked before inclusion. Extract the ZIP and run `install.ps1` to copy it into a new per-user folder and create a Start Menu shortcut, or run the executable in the extracted `app` folder. The installer checks that the executable, bundled OpenSSL DLL and inventoried Python runtime files match the package manifest before creating the installation folder. These checks detect missing or damaged files; the unsigned manifest does not establish package authenticity. Existing installation folders and shortcuts are not overwritten. The bundled Python includes the pinned PDF libraries, so PDF features can use it without a separate setup download. The package builder also bundles pinned Ollama 0.40.13 Windows and AMD GPU archives by default. This adds about 1.9 GB of downloads and requires at least 8 GiB of free space during packaging. Use `--ollama-archive-dir <path>` for offline copies of those exact archives. To reuse the runtime from a previously verified Waypoint ZIP, supply `--ollama-from-package <path> --ollama-package-sha256 <digest>`; the builder verifies that ZIP and each runtime file. Use `--no-ollama` to omit the runtime. The installer verifies the bundled runtime files before and after copying them; start it from Settings and install a model separately. Optionally, `--chromium-dir <path>` includes a supplied Chromium distribution containing `chrome.exe` and `LICENSES.chromium.html`. Its files are inventoried and checked before and after installation; the supplied distribution's provenance, redistribution rights, completeness and updates remain the packager's responsibility. Chromium snapshots do not update automatically. The default package does not yet provision a browser. The package is an unsigned prototype; Microsoft Visual C++ runtime may need separate installation, and document conversion requires LibreOffice to be bundled or separately installed. Redistribution of the GPU runtime and the complete dependency license inventory still need review; do not distribute the prototype bundle until that review is complete.

Before copying, the installer checks that the destination reports enough available space for the extracted app files plus a 512 MiB reserve; free space can still change during installation. The installer includes hidden package files and verifies the executable, OpenSSL and inventoried dependencies again after copying. This second verification increases installation time, especially with bundled LibreOffice. If installation fails after copying starts, the newly created directory is retained for inspection and no success is reported.

If Cargo used a custom target directory or target triple, pass `--build-dir <directory>` pointing to the profile directory printed by the build helper. Use `--release` when packaging a release build; the receipt must match the selected profile and files.

Packaging uses an installed LibreOffice distribution if available. Otherwise, on Windows, it downloads the pinned official LibreOffice 26.8.2 x64 MSI, verifies its SHA-256, and extracts it into a private build directory without installing it into the system. The download is approximately 359 MiB and provisioning requires at least 4 GiB of free disk space. For offline builds, pass `--libreoffice-msi <path>` with the matching pinned MSI, or `--libreoffice-dir <directory>` with a complete existing distribution. Use `--no-libreoffice` only to deliberately create an incomplete package. A failed extraction retains its staging directory for inspection. Bundling substantially increases package size and time; the installer checks the bundled files against the manifest.
