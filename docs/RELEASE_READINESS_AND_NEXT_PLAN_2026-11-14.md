# Release readiness and next implementation plan — 14 November 2026

## Assessment

**Smart Jobseeker is an integrated prototype, not a release candidate.** It is
still several major engineering and qualification stages away from release,
rather than one packaging or visual-polish pass. Substantial foundations exist,
but no varied source-to-final-review candidate journey has passed independent
whole-workflow acceptance. A completion percentage or calendar release date
would not be supported by the current evidence.

The most useful next estimation point is two complete, independently scored
candidate journeys followed by a frozen representative baseline. Those runs will
show whether remaining work is mostly defects within connected mechanisms or
missing capabilities across platform families. The user alone decides release;
this plan creates no release, application-send permission, branch or new goal.

Source: committed baseline `4ea8a3959c6f0e0b373336f33ef384affe5a4625` plus the
qualification/correction changes accompanying this review. Native reports retain
binary, source, model, input and controller hashes privately. Older gate/hosted
results keep their original scope. [This round's measured evidence](g1/REVIEWED_QUALIFICATION_ANSWERS_2026-11-14.md)
is separate from the targets below.

## Execution order

### 1. Fix typed answer shape and numeric grounding (R04, with R02/R13)

Use the existing grounded-answer and history-component mechanisms. Add a typed
projection for short text, numbers and units anchored to exact reviewed source
spans/IDs and the current field/question. Unit omission or conversion must have
an explicit source-unit/question-unit proof; a bare matching numeral or a model's
agreement alone is insufficient. Preserve the shared paragraph numeric guard.
Keep natural wording for prose while respecting single-value/native constraints.

Adversarial inputs must include years versus months, dates versus counts,
percentages, ranges, multiple subjects/roles, conflicting facts, missing precision,
unreviewed canaries and an unrelated field with the same number. Reuse the
unchanged current cases first: the development regression target is 4/4 correct
answerable fields, 0/4 unknown entries and no wrong/unverified source or entry.
This target is not a representative completion claim. Retain all earlier failures.

### 2. Connect two complete candidate journeys (R04/R06/R07/R08/R10/R12)

Drive the real local web interface headlessly. Include profile/qualifications,
PDF and DOCX CV/cover templates, supporting files and custom instructions. Find
permitted real listings through the UI's broad search, not only direct API job
insertion. Retain the original advertisement, classify freshness and prove that
an application route/panel can actually open. Keep unknown constraints and near-
duplicate holds; minor title differences never imply a different application.

Prepare factual, naturally worded CV/cover changes, convert all final attachments
to PDF, inspect every page and check extracted text/layout/ATS readability. These
checks cannot promise an employer's ATS rank or undetectable authorship. Candidate
history must never be rewritten to match the hiring employer.

Use faithful permitted saved forms and owned loopback interaction fixtures for
entry until R05 allows a broader scope. One journey should combine contacts,
PDFs, history and qualification answers; another should add conditional/repeated
rows, sections/tabs and a custom widget. Every action gets current native and
local-model visual evidence; no-progress, ambiguity, login and CAPTCHA walls
produce actionable review records. Do not bypass challenges or interact with
real employer fields while the current no-write limitation remains.

A journey passes only when its predeclared required fields, accepted attachments,
section progress, final native/visual review and complete immutable record agree.
Keep proposals, attempted/performed entries, original observations, unresolved
questions and outcomes distinct. Stop before delivery; create no submission grant.

### 3. Close lifecycle and write-isolation prerequisites (R01/R03/R05/R10)

Exercise script-triggered writes under innocent-looking controls, frames,
workers/popups, non-HTTP transports, redirects and ambiguous responses. Establish
OS/transport enforcement independently of the model's visual judgment. Preserve
all earlier diagnostic failures. Test restart/cancel recovery and one-use approval
consumption without automatic retry after an uncertain external write.

Measure Stop/cancellation deadlines and actual process-tree exit, including
uncollected sessions. Perform a bounded sustained-memory/idle-expiry qualification.
A zero-process snapshot is not a leak test. Preserve unrelated workloads, keep
headless operation and create no development services or scheduled tasks.

### 4. Freeze and evaluate representative coverage (R02/R03/R04/R07/R08/R09)

Freeze development versus held-out partitions before tuning. Include multiple
independent employers per underlying platform, different wording/order, languages,
layout/control families, templates and accessible source states. Public real CVs
and other personal material remain private and excluded from Git; fictional
checked fixtures provide reproducible published regressions.

Score exact-value/source/native/visual entry correctness separately from factual
prose quality, document acceptance and complete-to-final-review workflows. Report
all declared cases, eligible cases, manual walls, safe abstentions, failures and
unknowns. Never reclassify a failed case after seeing the outcome to improve a
completion denominator. Repeat matched cases for model/context/lesson promotion;
report host/RAM/VRAM scopes and incomplete runtime metadata honestly.

The engineering promotion target is zero critical incorrect/unverified performed
entries or unauthorized writes, with high complete-workflow coverage on the
predeclared eligible set. Establish the representative baseline before setting a
credible completion-rate promise; small fixture success cannot support universal
or one-in-a-million claims. Anonymous internet-connected technical research must
show useful, source-supported repair, not merely successful fetching. Lessons
need paired ablation/transfer evidence and must not replay stale selectors or
override current facts, observations or approvals.

### 5. Qualify installation, storage, email and the whole interface (R06/R10/R11/R12)

Run the supported same-OS/architecture Windows matrix on clean non-admin hosts,
including missing/interrupted/offline dependencies, custom paths, upgrades,
rollback, encrypted migration and backup/restore. Resolve/provision private tools
automatically; do not depend on this host's PATH, OpenSSL, Python, browser or
LibreOffice installation. Retain actionable degraded/offline outcomes.

Qualify the selected local model/context on the 16 GiB GPU target with measured
host RAM protection. GPU reserve may be small, but host exhaustion is never an
accepted fallback. Reuse caches, serialize expensive inference and verify owned
teardown; keep API-reported VRAM, WDDM adapter usage and host commit distinct.

Exercise email settings/credential storage, draft preparation/correlation and
explicitly authorized self-tests or owned mail fixtures. Send no application email.
Review all screens, settings, license/dialog and error states within these journeys,
including mouse resizing and browser zoom. Use shared styles/interactions and
actual screenshots; geometry alone does not establish visual quality.

### 6. Assemble the user decision dossier (R14)

Bind supported capabilities, completed/failed cases, build/install artifacts,
model/configuration/input identities, dependency/license evidence and current
hosted checks to the same source. List unresolved detector findings and unsupported
scope. Do not manually close, dismiss, ignore or suppress any finding. Do not
publish a release, merge a separate branch or send an application as part of this
plan. Open findings alone neither prove failure nor establish readiness; the user
makes the release decision with the complete evidence.
