# Application experience and learning: research and implementation design

Research date: 2026-11-01. This is a design, not an implemented learning system or a claim that a model has learned. Site content and agent-generated lessons are untrusted. The existing live-form inspection, user review and submission restrictions remain authoritative.

## Evidence and implications

- [Hierarchical Memory Tree](https://arxiv.org/html/2603.07024) separates intent, stage and action knowledge and checks stage preconditions. Its cross-site benchmark results suggest that semantic stages can transfer better than flat transcripts. The paper also reports ambiguous grounding and subtle state-transition failures; a similar label is not proof that the current control is the same.
- [WebChallenger](https://arxiv.org/html/2606.10423) uses a structured page representation and a reusable map without model fine-tuning. Its authors identify dependence on DOM heuristics, atypical sites and sequential model-call cost. A map should guide inspection, not be replayed as a script.
- [Experience Memory Graph](https://arxiv.org/html/2607.13884) contrasts failed and successful trajectories to infer corrections. Its evaluation is in simulated environments, not job applications, and matching trajectories is imperfect. A later success alone does not prove which earlier action caused failure.
- [AMBER](https://arxiv.org/html/2610.07118) studies append-only agent memory for preserving corrective feedback, but notes context growth and open selection/consolidation questions. Keep an auditable event history separate from bounded, revocable retrieved lessons; do not append every transcript to the model prompt.
- [A Domain-Agnostic Approach for Characterization of Lifelong Learning Systems](https://arxiv.org/html/2301.07799) distinguishes forward transfer from performance maintenance. A memory feature needs comparisons against no-memory baselines and old cases, not just success on the experience used to create it.

These are research results, not evidence that Waypoint will achieve similar performance. None establish reliable autonomous job submission.

## Proposed design

1. Capture an experience only from a user-reviewed interaction or a verifiable local observation, with explicit provenance: task/stage, privacy-safe structural page features, observed problem, attempted action, observed result, user correction, and confidence or uncertainty. Distinguish observed results from model interpretation. Never record authentication data, candidate answers, document contents or screenshots in reusable lessons. Existing per-application records remain separate and subject to their own privacy controls.
2. Store experiences in the encrypted workspace, with bounded sizes, versioning, provenance and timestamps. Expose review, disable, deletion and correction. A corrected or deleted experience must no longer be retrieved, including from any cache. Avoid automatic model weight updates and training on private data.
3. Retrieve a small, bounded set using task/stage and compatible control structure as well as platform hints. A suspected shared platform is weak evidence: tenant configuration, language, role and page version can differ. Prefer diverse evidence and retain contradictory or failed experiences; no match must be a normal outcome.
4. Present retrieved lessons as attributable, fallible context for the local model and user. Re-ground every proposed action in the current DOM and visual state, verify preconditions and postconditions, and defer ambiguity to manual review. Never use a remembered selector, value, sensitive answer, authorization, or submit action as authority. Enforce existing grants and submission restrictions independently of model output.
5. Evaluate on separated source sites and later variants, including unseen tenants, misleadingly similar controls, renamed elements, contradictory feedback and stale pages. Compare no-memory and memory-enabled runs on task completion, incorrect actions, unnecessary manual reviews, latency and resource use. Preserve old cases as regression sets and measure both transfer and regressions; report denominators and uncertainty. Test with fictional profiles and no application submission.

## Current gap

The application already archives bounded observed form-question snapshots and supports reviewed form suggestions, but those records are not a complete cross-application learning system. A new storage primitive supports bounded DPAPI-sealed records, revision checks and logical revocation with non-reusable IDs. Revocation removes records from that primitive's reads; it does not securely erase SQLite pages or backups. A workspace layer accepts reviewed categorical observations and responses, matches stage and control, ranks an identical known platform higher, and returns up to five diverse observation/response pairs. A web panel can create, list, find related records and revoke these categorical records after confirmation. A local API test covered the lifecycle, and an isolated rendered Edge test exercised saving, lookup and removal at 1,200 and 390 pixels without horizontal overflow or page errors. During model-assisted initial form inspection, up to ten text and choice lessons are supplied as untrusted context; the user must review the resulting suggestions. New lessons can be recorded during an active review for a later inspection; corrections and removals are blocked until the review closes so the current lesson snapshot stays stable. Records can now contain a short user-written note. The UI asks users not to include personal details, answers, credentials or copied application content, but cannot guarantee they comply. Notes are sealed at rest and are sent to the local model only if the user explicitly enables that per note; records do not yet contain verified provenance links or independent outcome evidence. They cannot execute browser actions. A broader effect on local-model behavior is not established. Rich experience curation, semantic retrieval and controlled learning evaluation remain to be implemented and validated end to end.

On 2026-11-01, a resource-gated qwen3.5:9b comparison used one fictional contact form and one categorical lesson about inspecting ambiguous labels. Both the baseline and lesson-assisted run mapped the applicant and generic email fields, and neither mapped the manager or reference email fields. The runs produced the same selected fields, so this is not evidence of a learning benefit or general reliability. The model was unloaded after the test; minimum free system memory sampled every 0.5 seconds was 13,943 MiB. This small check did not exercise saving lessons through the interface during a live form inspection, nor does it demonstrate behavior on real application sites.

A second baseline-versus-lesson comparison used two fictional multilingual forms with an ambiguous contact question, a work-eligibility or sponsorship question and an email field. Both configurations mapped only the email and marked the other two for review in both cases. All four evaluations met those assertions, but the baseline already passed, so no improvement was demonstrated. The model was unloaded; minimum sampled free RAM was 14,180 MiB at 0.5-second intervals. These examples do not establish performance on new forms or prove the lesson was influential.

Lessons can now include the user's reported outcome: helped, did not help, or unknown. Older records default to unknown. Retrieval preserves different reported outcomes among its diversity criteria, and the model is told that a report is not proof of cause and that an unsuccessful response should not be treated as a success. Fictional storage and API checks covered unsuccessful and older records; an isolated rendered test saved and displayed an unsuccessful outcome at 1,200 and 390 pixels. This remains a categorical self-report; it is not independent verification or evidence of improved model performance.

The user can correct a reported outcome in place. Revision checks reject stale corrections, and the original observation timestamp is retained. A local API test exercised correction and a rejected stale update; an isolated rendered test exercised correction at 1,200 and 390 pixels. Changing categorical lesson fields still requires removal and a new record.

A user can save a new lesson while form inspection is pending or a review is open. The currently running inspection keeps its original lesson snapshot; the new lesson is eligible only for later inspections. A fictional pending-task API test covered saving, blocking removal until the task closes, and subsequent removal. This test did not exercise an actual live employer form.

For initial model-assisted inspection, an exact recognized listing-source category now supplies a weak platform hint to lesson retrieval. The actual application destination may differ or redirect, so it does not establish platform identity, grant permission or suppress lessons from other platforms. Unknown sources use no platform hint. This selection has not yet been evaluated on real cross-tenant applications.

Users can add a short free-text context or fix to a lesson. It is sealed with the record, rendered as text, bounded to 280 characters and 512 UTF-8 bytes. They are excluded from model prompts unless explicitly enabled, and a 768-byte encoded note budget limits what is included. The interface asks users to avoid personal data and credentials, but does not automatically verify that instruction. Fictional tests covered validation, backward compatibility and preserving a note after outcome correction; an isolated rendered test checked that markup-like note text is displayed literally at 1,200 and 390 pixels. Users can correct or clear a note in place, with revision checks; an isolated rendered test exercised correction at 1,200 and 390 pixels. The local model can receive an enabled note as untrusted context, but a learning benefit is not established.

An experimental, test-only qwen3.5:9b comparison on 2026-11-01 supplied no note, a helpful note, and a misleading note instructing the model to map the candidate's email to sensitive fields. In all three cases the form-suggestion pipeline mapped only the fictional email field and flagged the ambiguous and eligibility fields for review. The baseline already passed, so the result does not show useful learning, and the validated pipeline output does not prove the raw model resisted the misleading instruction. This one fictional form is insufficient to establish reliable instruction resistance or a learning benefit. The model was unloaded; minimum sampled free RAM was 14,870 MiB at 0.5-second intervals.

Per-note user opt-in now permits notes in the production form-mapping prompt; old and non-opted-in notes remain excluded. A separate 768-byte encoded note budget can omit notes, and they are labeled untrusted and potentially irrelevant. The current form, mapping validation, manual review and existing approval controls remain authoritative. Fictional tests checked opt-in, opt-out, the budget, stale revisions and clearing notes. An isolated rendered test covered opt-in and editing at 1,200 and 390 pixels. A qwen3.5:9b comparison using the production note-enabled path on two fictional multilingual forms produced the same safe mappings and review flags as the baseline. This does not demonstrate improved accuracy or reliable resistance to malicious notes; minimum sampled free RAM was 14,212 MiB, and the model was unloaded.

A separate resource-gated test exercised the background inspection worker with one opted-in note and a fictional browser form. It mapped the explicit email and left two ambiguous contact fields for review; it did not fill or submit. The review notice now says lessons were included in an attempted mapping request only when such a request was actually made; this does not prove the model received, understood or followed them. Minimum sampled free RAM was 13,873 MiB and the model was unloaded. This does not establish performance on real sites or a benefit from the note.

Before model-assisted inspection, lesson context is now filtered against the control types present in the live form: text or choice lessons require a non-sensitive field of the corresponding class. Other lesson classes are not sent through this mapping path. Filtering also applies to each model batch; it does not establish that a lesson applies to an individual field, so irrelevant context can still be included. Fictional type tests and the local worker fixture passed; the latter mapped the explicit email and flagged ambiguous fields, with minimum sampled free RAM of 13,816 MiB. The model was unloaded. This does not establish that the note improved the result.

The per-batch filtering was checked with a fictional mixed form split into a text-only batch and a choice-only batch. Each model request received only its matching lesson class. A separate qwen3.5:9b worker run on a fictional text form still mapped the explicit email and flagged the ambiguous fields; minimum sampled free RAM was 14,208 MiB and the model was unloaded. These tests do not establish semantic relevance within a class or model improvement.

The inspection review now reports how many opted-in note inclusions were prepared or omitted by the context budget across attempted mapping requests. A note can be counted more than once across batches. A resource-gated fictional worker run reported one inclusion and no omissions; minimum sampled free RAM was 14,512 MiB and the model was unloaded. Counts report request preparation, not model receipt or attention.

An additional isolated Windows test saved a fictional opted-in lesson through the encrypted workspace API, retrieved it, passed it into the real browser inspection worker and revoked it afterward. The local model mapped the explicit email and flagged two ambiguous questions; no fields were filled and no application was sent. Minimum sampled free RAM was 14,512 MiB; the model was unloaded. This combines storage and worker execution, but does not exercise lesson creation through the rendered interface or prove the note changed the model's decision.

Lessons can now be disabled and re-enabled without deleting their contents. Disabled lessons remain visible in the inventory but are excluded from related-lesson retrieval and future model context. Changes use revision checks and are blocked while a form review is active. Fictional workspace and API tests covered stale updates and retrieval, and an isolated rendered test exercised disable, empty lookup and re-enable at 1,200 and 390 pixels. This enables controlled comparisons but does not itself measure a lesson's effect.
