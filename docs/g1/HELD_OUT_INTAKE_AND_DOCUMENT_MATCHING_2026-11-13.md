## Generic document proposals

The new `attachment_mapping` component asks the local model to match native
file controls to an explicit caller-owned document catalog. Document purposes
are supplied as descriptions and opaque IDs; filesystem paths and file contents
are withheld. It supports arbitrary catalog purposes, including certificates,
without embedding employer or field-label aliases. The saved-copy rehearsal
currently supplies only its two fictional PDF fixtures.

The request includes native field labels and named section context as untrusted
data. Model output may select a supplied document ID or request review. Native
selectors are restored by validated opaque field identities; the model cannot
invent selectors, filenames, files or approval. Sensitive controls stay manual.
Unknown/duplicate controls, unavailable documents, incomplete/malformed output
and budget overruns refuse the proposal. All form selectors must be unique,
including collisions between file and nonfile controls.

The component uses the existing local structured-inference adapter and a
registered schema, with the same resident model/digest, private-owner and
memory/cancellation guards. There is at most one bounded matching request per
view, up to 16 upload controls/documents and an 8,000-byte prompt. The existing
rehearsal action and section budgets remain; this is not full-form promotion.
Failure leaves uploads unchosen, records a review result and does not fall back
to keyword matching. The interface exposes unresolved document choices.

An accepted proposal still passes the existing current native target checks,
independent before/after local vision and attachment-byte verification. Only
the contained fictional/saved-copy path consumes these proposals. This change
does not authorize live uploads, grant approval or add submission capability.
